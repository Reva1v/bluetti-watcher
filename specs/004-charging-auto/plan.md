# Plan: 004 — Автоматическое переключение режима зарядки

Формат короткий, как у 002: исследование, модель данных и контракт собраны здесь.

## Решения

- **Чистое ядро** `src/decision/charging.rs` (без I/O и часов):
  - `ChargingAuto { light_pending: bool, high_water: Option<u8>, off_at: Option<Ts>, want: Option<Want>, backoff: Option<Backoff> }`,
    хранится в `meta.charging_auto`, отдельно от `DecisionState`: `guards::reset` сбрасывает то состояние, а это должно выжить.
  - `Want { mode: ChargingMode, why: Why }`, где `Why` — `Light { soc }`, `Soc { soc }`, `Shutdown`.
  - `update(&mut auto, Seen { soc, mains, mains_confirmed, outage }, current_mode, now, cfg) -> Option<Want>` — только по
    принятому показанию:
    1. идёт пауза после выключения (`off_at` моложе 2 мин) — ничего не делать: запись «Тихая» иначе отменилась бы, пока
       Windows ещё завершает работу. После паузы `off_at` очищается. Часы ушли назад — пауза считается прошедшей;
    2. `outage` — `light_pending = true`, незавершённая запись снимается;
    3. `light_pending` и сеть подтверждена — цель по уровню (FR-002), `high_water = soc`, `light_pending = false`;
    4. иначе при `mains == On` — переход `high_water < порог ≤ soc` для 50 и 80 (больший порог побеждает), `high_water = max`.
       Первое показание только запоминает `high_water`;
    5. цель совпала с `current_mode` — записи нет. Иначе `want` живёт до успеха, повтор по `guards::backoff_delay`.
  - `report(&mut auto, ok, now)`, `manual(&mut auto)` (снимает `want` и бэкофф, FR-009), `shutdown(&mut auto, now)`
    (`off_at = now`, `light_pending = true`, `want = None`).
  - `high_water` не падает внутри периода с сетью, поэтому качание 79↔80 не даёт новых записей (сценарий 2.3).
- **Перезапуск сервиса** (обновление, сбой): `light_pending` не взводится, ручной выбор цел; порог, пройденный за время
  простоя, срабатывает через `high_water`. Запуск ПК после выключения даёт включение света через сохранённый `light_pending`.
- **Сервис** (`service.rs`):
  - `tick`: `decide` начинает возвращать ещё и статус; при `Accepted` и `cfg.charging_auto.enabled` — `charging::update`,
    затем запись. `--dry-run`: только лог, `report(ok)`. Успех: событие `charging-mode` с причиной и `data { mode, reason }`.
    Неудача: `fail` → `action-failed` и `lastError` на дашборде.
  - `cycle`: нажатие на чипе вызывает `charging::manual` до записи.
  - `run`: `Channels.shutdown` забирается в локальную переменную; `select!` с `biased` ждёт её и в простое, и вокруг `cycle`.
    Цикл можно бросить на любом `await`: между ними весь код синхронный, а транспорт WinRT отменяется при `drop`.
  - `on_shutdown(req)`: режим уже «Тихая» или `--dry-run` — записи нет. Иначе до двух попыток внутри `timeout` 13 с. Потом
    `charging::shutdown`, сохранить состояние, ответить `req.done`.
- **Сигнал выключения** `src/shutdown.rs`:
  - свой поток со скрытым окном верхнего уровня (message-only окна `WM_QUERYENDSESSION` не получают) и `GetMessageW`.
    `SetProcessShutdownParameters(0x3FF, 0)`, чтобы получить сигнал среди первых. Запускается только при `enabled = true`;
  - `WM_QUERYENDSESSION` с `lParam == 0` (выключение и перезагрузка). Выход из сеанса, `ENDSESSION_CLOSEAPP` и
    `ENDSESSION_CRITICAL` не считаются: режим не трогаем, отвечаем сразу;
  - `ShutdownBlockReasonCreate`, отправка запроса сервису, `recv_timeout(15 с)`, `ShutdownBlockReasonDestroy`, ответ `TRUE`.
  - Сон и гибернацию окно не обрабатывает (FR-004).
  - Новые features `windows`: `Win32_System_Shutdown`, `Win32_Graphics_Gdi`. Новых зависимостей нет.
- **Конфиг** `[charging_auto]`: `enabled = false`, `turbo_below = 20`, `light_silent_at = 75`, `standard_at = 50`, `silent_at = 80`. Нарушен порядок
  `turbo_below ≤ standard_at < silent_at` или `turbo_below < light_silent_at ≤ silent_at` — значения по умолчанию и предупреждение.
- **Дашборд** не меняется: чип показывает прочитанный режим, события идут в историю.

## Исследование

- Обмен со станцией занимает 0,7–0,9 с (три замера чтения через `/api/check`, 2026-11-02). Лимита 15 с хватает с запасом.
  Запись по кнопке живьём ещё не подтверждена (003), её время не измерено.
- Служба Bluetooth останавливается после завершения приложений пользователя, поэтому на `WM_QUERYENDSESSION` запись возможна.
  Проверяется только на реальном выключении: см. проверку владельцем.
- Отвергнуто: `SetConsoleCtrlHandler` (без консоли процесс сигнал о выключении не получит), задача планировщика на событие
  выключения (нужны права администратора, срабатывает поздно), `PBT_APMSUSPEND` (не нужен: сон и гибернация не входят в правило).

## Контракт: `config.toml`

```toml
[charging_auto]
enabled = true     # по умолчанию false: запись только по кнопке
turbo_below = 20   # свет включился, заряд ниже: «Турбо»
light_silent_at = 75  # свет включился, заряд не ниже: «Тихая»
standard_at = 50   # заряд дошёл: «Стандартная»
silent_at = 80     # заряд дошёл: «Тихая»
```

При включении света заряд от `turbo_below` до `light_silent_at` даёт «Стандартная», от `light_silent_at` — «Тихая».

## Конституция

- I (3.0.0): запись только по правилу, включённому в конфиге, и только через `charging_mode_request`. Выключено по умолчанию.
- II: срабатывают только принятые показания, сеть — подтверждённая. Питание ПК не затронуто.
- III (3.0.0): окно скрыто и создаётся только при включённой автоматике; придерживание не дольше 15 с.
- IV, VI: один `.exe`, без новых зависимостей; настройка решает задачу владельца.
- V: решения в `decision/charging.rs` с временем параметром. Окно — тонкий адаптер, его проверяет владелец.
- Отступлений нет.

## Тесты

- `decision/charging`: все сценарии спеки: границы 19/20/74/75, порядок 15 → 50 → 80 (ровно три режима), качание у порога,
  блик сети, рост без сети, совпадение с текущим режимом, неизвестный режим, бэкофф, `manual`, пауза после `shutdown`,
  перезапуск (состояние через JSON), запуск после выключения.
- `service`: запись по порогу и отсутствие записи при `enabled = false`; отвергнутое показание не пишет; `--dry-run`;
  ошибка записи и повтор; `on_shutdown` пишет «Тихая», молчит при «Тихая», отвечает при ошибке; сигнал обрывает зависшее
  чтение; после `on_shutdown` следующий цикл не возвращает режим.
- `config`: разбор и проверка порядка порогов.
- `tests/protocol.rs`: существующая проверка исходящих кадров остаётся без изменений (SC-005).
